# 单元测试、教程与数据设计

## 工具与依据

选用 Node.js 内置 `node:test` 和 `node:assert/strict`。页面不需要 Node.js，只有开发时复跑测试需要 Node.js 22+。测试直接调用业务和存储函数，没有依赖浏览器，也不需要安装 Mocha 等第三方框架。

参考 [Node.js Test runner 官方文档](https://nodejs.org/api/test.html) 的最小示例理解“准备输入 → 执行函数 → 断言结果 → 独立运行”；参考 [MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage) 与 [Clipboard.writeText](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText) 确定存储和剪贴板的异常路径。个人学习经历请由本人补充，文档只说明实际使用的方法。

## 五步复跑教程

1. 安装 Node.js 22 或更新版本。
2. 打开项目目录，在终端确认 `node --version`。
3. 执行 `npm test`；项目使用内置模块，**不需要 npm install**。
4. 查看末尾 `tests / pass / fail`；有失败时找到用例名称、断言和输入。
5. 修改后重跑。需要覆盖率时运行 `npm run test:coverage`。

新写一个测试文件时可以采用：

```js
const { test } = require('node:test');
const assert = require('node:assert/strict');
const C = require('../js/core.js');

test('不存在的记录不能更新', () => {
  const result = C.completePost([], 'missing', 'owner-a');
  assert.equal(result.ok, false);
  assert.equal(result.error, '这条信息不存在。');
});
```

测试名写明预期。`assert` 不符合预期即抛出错误，测试工具自动统计为失败。不要只判断函数有没有抛异常；应检查状态、返回数据、原输入是否被改变以及存储内容。

## 白盒用例设计

先从代码的条件分支列出路径：合法 / 非法输入、找到 / 找不到记录、本人 / 他人 / 样例、进行中 / 已完成、写入成功 / 抛异常。再用等价类和边界值组织数据，避免 10 个用例都在重复成功路径。

| 编号 | 函数 / 模块 | 重点与预期 |
| --- | --- | --- |
| 01–03 | createPost / validatePost | 两类正常发布、初始状态、去除首尾空格 |
| 04 | validatePost | 空串和全空格的必填项均失败 |
| 05–06 | validatePost | 名称 40 / 41；描述 4 / 5 / 500 / 501 字边界 |
| 07–09 | validatePost / isDate | 非法枚举、闰年、无效日历日期、今天及未来 |
| 10–11 | validatePost | 四种联系方式的有效 / 无效格式 |
| 12 | createPost | 没有 ownerId 不得创建 |
| 13–14 | completePost | 本人寻物 → 已找到，招领 → 已归还 |
| 15–17 | canManage / completePost | 他人、空身份、演示记录、不存在 ID、重复完成被拒绝 |
| 18 | completePost | 原始数组和记录保持不变 |
| 19–21 | queryPosts | 名称 / 描述 / 地点；多词 AND；全半角 / 大小写；空词与无结果 |
| 22–26 | queryPosts | 组合筛选、本人的记录、排序、完成状态过滤 |
| 27–28 | escapeHTML / isPhoto | 特殊字符转义，脚本 / SVG / 远程图片 / 过大数据被拒绝 |
| 29–30 | load / save | 初次初始化、身份稳定、记录及完成状态读回 |
| 31–32 | load / save | 损坏 JSON 保留原始内容，非法版本和重复 ID 拒绝写入 |
| 33 | load / save | SecurityError / QuotaExceededError 返回明确失败 |
| 34–36 | 草稿存储 | 写入 / 恢复 / 清除、损坏内容、未知字段、异常反馈 |
| 37–39 | validPost / validatePost | 存储结构损坏、非对象输入、原型链属性名绕过尝试 |

例如，以下测试验证状态更新的权限边界，而不是仅验证按钮有没有显示：

```js
test('非发布者、空身份不可修改', () => {
  assert.equal(C.completePost([post()], 'post-a', 'owner-b').ok, false);
  assert.equal(C.canManage(post(), ''), false);
});
```

测试中的 `post()` 用固定日期、固定 ID 创建有效样例，再只改变本用例关注的字段。这使失败来源更容易定位，也避免依赖真实姓名、联系方式和当前机器已有数据。

## 面对异常输入

预先考虑空白、过长文本、不可能日期、未来日期、不合法联系方式、HTML 字符、恶意类型名、坏图片、重复操作、缺失记录、非本人修改、损坏 JSON 和存储容量不足。使用内存存储替身主动抛出异常，验证失败不会被当作成功。

白盒测试覆盖纯逻辑，浏览器回归验证 DOM 事件、页面路由、表单、图片处理和持久化的配合。两者职责不同，不能用函数覆盖率声称整个界面已经 100% 覆盖。

## 可选 Chrome 浏览器回归

需要额外安装 Playwright，并准备 Google Chrome：

```sh
npm install --no-save --package-lock=false playwright
node scripts/browser-test.cjs
```

脚本默认找已安装的 Chrome。若使用便携版 Chrome for Testing，在 PowerShell 设置：

```powershell
$env:CHROME_BIN = 'C:\path\to\chrome.exe'
node scripts/browser-test.cjs
```

本次执行使用官方 Chrome for Testing 154.0.8037.57、Windows、1440×1000 / 390×844，关闭网络，用 `file://` 打开入口。每次启动独立的测试上下文，不碰用户日常 Chrome 的数据。脚本输出 JSON 报告并生成界面截图。

剪贴板测试使用成功 / 拒绝两种替身，验证界面反馈及手动选择入口；未声称每台机器的系统剪贴板权限均已实测。正式提交前，两名同学应在自己的 Chrome 上实际点击复制一次。

## 自动执行

`npm test` 一条命令即可运行。仓库提供 GitHub Actions，push 和 PR 后自动复跑单元测试，也可手动触发；首次云端结果需查看 Actions 页面。单元测试不需要网络服务或私密凭据。浏览器回归作为本地可选检查，不要求助教配置浏览器自动化环境。

## 测试评价

39 个单元用例涵盖主要规则与异常路径；19 组浏览器回归覆盖两类完整流程及手机排版。覆盖率的统计范围只有 `core.js` 和 `store.js`，不包括整个应用。未覆盖真实用户多人并发、真实认证、跨设备同步、大规模数据性能、全部 Chrome 历史版本或所有读屏软件。本项目也没有声称具备这些能力。
